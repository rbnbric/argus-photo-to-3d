## Next cloud asset stage

The next Nebius AI Cloud stage can move asset generation or full-resolution camera parity to the cloud. `ship_gof_backend.py` is an actual CUDA surface-evaluation path, but its pinned extension and scene dependencies must be packaged and qualified on the selected cloud GPU before it is a runnable job. The fox material and original-camera comparison in `ship_fox_material_model.py` and `ship_fox_material_camera_compare.py` is the output-parity target: it loads the GLB, texture atlases, original photographs and masks, twelve camera transforms, and light receipt, then writes images and a per-view report. Those two scripts use NumPy/SciPy and trimesh, with no demonstrated CUDA path; merely moving them into a GPU container would not prove GPU processing. Their current runner uses a pinned local Docker image and Ahab-mounted working tree. Neither runtime and source package is ready for Nebius yet.

For a future paid asset-generation job, package one immutable input manifest covering its exact scene data, photos, masks, cameras, script revision, pinned extension, and container image. Preserve source ownership and camera bindings. Write a retrievable mesh, field, or rendered images plus a report; logs alone are insufficient. Compare that artifact against a frozen local result using the same cameras and record metrics and differences. Include the fox fixed-camera material comparison if the cloud stage produces a compatible surface or asset; do not substitute its CPU execution for CUDA evidence.

Do not promote geometry or materials merely because the cloud job succeeds. Preserve the local report's `diagnostic` status and the existing failed or conditional qualification gates. The cloud acceptance gate is reproducible execution and artifact parity, not a claim that the fox is already game ready.
